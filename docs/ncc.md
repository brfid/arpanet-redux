## Product shape

The useful product is a topology-first network board with bounded read-only views over separate validated contracts:

1. **Completed-run mode:** reconstruct the configured route, lifecycle transitions, normalized IMP and host observations, application proof, and acceptance verdict from a safe derived summary. This is the first end-to-end deliverable because it can be tested deterministically and does not require a new live simulator attachment.
2. **Progressive observation:** consume validated append-only records while a bounded harness run is active, preserve explicit incomplete-tail and generation status, and keep every inference in Python. The controller-owned lifecycle stream retains its version-1 direct-only contract. The historical-report display observes the separate version-1/version-2 historical-event sidecar and owns freshness plus completed-summary handoff; the message-journey display observes its separate version-1 sidecar without inventing a global clock or completed verdict.
3. **Message-journey diagnosis:** show the configured Network UNIX-to-ITS route as twelve direct-route or sixteen failover-route request/reply crossings while keeping direct H316 observations, harness-derived connected-peer delivery, reducer assessments, missing evidence, and exact trace-window provenance inspectable.
4. **Historical NCC telemetry:** attach a project-authored receiver at host 0 of BBN IMP 5 and feed genuine IMP status and throughput reports into the event stream. The ingress adapter validates and decodes the original Type 301 and patched Type 303 trouble-report wire forms plus Type 302 throughput, attributes each from the old-style leader, and preserves the on-wire code. Throughput counters remain cumulative values, not rates.
5. **Original NCC compatibility:** investigate booting the preserved 1971 NCC System 52 only after the required host interface, report generation, checksum, console, and lightbox behavior are understood. This is not required for the first useful console.

The browser interface is observability-only. Historical remote loading, core transfer, DDT, recovery, guest input, link switching, and simulator lifecycle controls are neither implied by the word “console” nor first-version browser features. A separate terminal runner may own one complete already-supported formal scenario and its exact stop path without giving the board process authority over a simulator.

## Operator model

The steady display combines two historically distinct artifacts:

- A stable mid-1970s logical map supplies the spatial index. Positions do not move when state changes; IMPs and TIPs form the main graph and hosts attach as leaves.
- NCC behavior supplies time, diagnosis, and attention: current versus stale observations, directional line states, an ordered event log, alarm priority, acknowledgement, and explicit uncertainty.

Traffic animation and simulator-process health are optional explanatory layers. Neither substitutes for evidence that a guest application used the intended IMP path.

## Evidence model

Every displayed conclusion must be traceable to normalized observations. The model keeps these categories distinct:

| Category | Examples | Display rule |
|---|---|---|
| Configured fact | IMP identity, host attachment, expected link, intended route | Show as topology, not as evidence that the component ran |
| Historical-network observation | Trouble report, host-interface state, modem endpoint state | Attribute to the reporting IMP and retain observation time |
| Harness observation | Process start/exit, console readiness marker, watchdog state | Identify as modern simulator or controller evidence |
| Application evidence | Guest command, remote response, correlated payload digest | Tie directly to the acceptance gate it supports |
| Inference | IMP isolated by partition, complete line down, likely failure location | Label as a conclusion and retain the observations and nominal topology used to derive it |
| Missing evidence | Timeout, absent report, incomplete marker sequence | Show unknown or stale; do not silently convert absence into down |

The completed-run summary should contain only project-authored or safely derived data. Raw simulator logs, historical messages, disk images, and third-party material remain in the external laboratory. A summary may contain safe pointers to external evidence, but the viewer must still work when those local files are unavailable.

## Normalized contract

Completed-summary schema versions 1 and 2 are accepted. Their stable concerns are:

- schema version, run identity, observation clock, and source provenance;
- nominal topology with stable component and endpoint identities plus fixed display positions;
- ordered observations and lifecycle transitions;
- derived component and path states, each with supporting observation identifiers;
- acceptance-gate verdicts and the application evidence supporting each verdict;
- explicit unknown, stale, incomplete, and contradictory states;
- optional external evidence references that are never required repository fixtures.

The accepted version-1 application contract and its alternatives are in [ADR-005](adr/0005-ncc-run-summary-contract.md). Version 2, accepted in [ADR-012](adr/0012-ncc-network-behavior-summary-v2.md), adds evidence-closed network-behavior gates and the reducer's looped and directional line states while retaining version-1 reads. `ncc.run_summary` validates both profiles. `ncc.two_its_summary` continues to write version 1 from only the formal two-ITS manifest, outcome, and sentinel evidence; its project-authored nominal topology input is `ncc.topology`, not a second controller configuration. It does not parse raw logs, control processes, or give an unavailable external-evidence locator semantic effect.

`ncc.live` writes one controller-owned header followed by flushed JSON Lines observations. The header carries the same version-1 nominal topology, run identity, provenance, and a staleness interval; each later line uses the version-1 direct-observation envelope and is validated against that topology. It has no derived states or gate verdicts, because those require the completed formal result and remain the adapter's responsibility. A reader ignores an incomplete final line, retains the nominal topology and last direct state, and marks only expired direct states as stale. It never attaches to or controls the simulator.

`ncc.historical_display` is an in-memory view over `ncc.historical_events`, the shared report-line mapping, and `ncc.reconciliation`; it is not another persisted schema. It exposes whether an interrupted final JSONL record was ignored and identifies append, truncation, replacement, restart, and run-identity changes without carrying observations across generations. Snapshots take an explicit observation clock, use the reducer's strict greater-than report-timeout boundary, retain each endpoint's last direct state and source, and give paired line conclusions separate in-memory authority. `ncc.historical_server` binds only IPv4 loopback, accepts GET and HEAD, exposes no arbitrary file route, and sends the browser an already-resolved view. When a supported result becomes formally terminal, it derives the existing version-2 summary, compares final mapped line state and exact `observation:historical:<sequence>` support against the last-event live reduction, and exposes the completed viewer only after exact agreement.

The existing `NccEvent` is one input form, not the complete run-summary schema. `ncc.reconciliation` pairs direct Type 301/patched Type 303 endpoint observations against a typed nominal topology and makes plus/minus direction, staleness, neighbor/configuration contradiction, and a narrow partition inference explicit. `nominal_topology_from_shared` constructs that input only from reciprocal `first_report_line` and `second_report_line` identities on an existing shared modem binding; it never infers a report line from `MI1`. The two-IMP project topology maps the exact observed IMP 5 line 1 and IMP 6 line 1 pair, and its retained exact sidecar reduces the final fresh observations to `up` with support sequences 103 and 114. The alternate-path topology reuses only that mapping; its canonical exact sidecar reduces the last pre-cut pair to `up` at sequences 80 and 91 and the final pair to `down` at sequences 377 and 387. A mapped down endpoint may omit the neighbor cleared by the recovered firmware, but a supplied wrong neighbor and an up endpoint without its configured neighbor remain contradictory. `ncc.historical_summary` now bridges only supported completed fault and loopback results into a version-2 final snapshot after revalidating the manifest, supplied topology digest, formal verdict, reducer state, and exact observation support. Unmapped alternate lines remain topology only, and the adapter neither modifies the external result nor grants the live stream inference authority. [ADR-006](adr/0006-ncc-line-reconciliation.md), [ADR-010](adr/0010-ncc-down-report-neighbor-absence.md), and [ADR-012](adr/0012-ncc-network-behavior-summary-v2.md) own these boundaries; the reducer must not be embedded in the decoder or browser.

`ncc.message_journey` is a separate source-only, in-memory diagnostic boundary. It derives every host and modem crossing from a named normalized route whose endpoint pairs must also have existing shared host-interface or modem bindings. Direct observations retain component and interface identity, ingress or egress direction, source-local sequence, optional source-local simulator tick and transport sequence, safely decoded 1822/NCP fields, a content SHA-256 correlation fingerprint, provenance, and optional opaque external evidence references. Its pure reducer compares request and reply observations without ordering independent sources against one another, rejects unknown topology identities and malformed correlations, and retains direct-observation identifiers for every conclusion. Absence remains missing evidence or wholly unknown, never a component-down claim.

`ncc.message_journey_stream` persists that existing model in a separate version-1 JSON Lines sidecar. Its header binds one formal run, the complete shared topology, the expected journey, source provenance, and the exact start/end offsets and SHA-256 of each consumed H316 trace slice. Observation order is explicitly emission-only, not a cross-simulator clock. Its reader tolerates only an interrupted final record and recomputes the existing reducer diagnosis; a terminal record that disagrees fails closed. [ADR-013](adr/0013-ncc-message-journey-stream.md) owns this additive contract and keeps it separate from completed summaries, controller-live observations, and historical reports.

`ncc.journey_display` is a deterministic in-memory projection over that reader and reducer, not another persisted schema. It reports complete-prefix, incomplete-tail, terminal, and stream-generation status; projects configured components and crossings from the already-validated expected journey; and labels direct H316, harness-derived connected-peer, configured-only, and in-memory reducer authority separately. Missing boundary support remains reducer context rather than an observation at the missing socket. `ncc.journey_server` binds only IPv4 loopback, accepts GET and HEAD, exposes no arbitrary file route, and sends a presentation-ready snapshot to `ncc.journey_viewer`. The browser uses source-local sequence, optional tick and transport identity, decoded fields, provenance, and byte-window metadata only for inspection; it never orders independent clocks, correlates packets, or assigns evidence to a boundary. A terminal view records exact persisted/reducer agreement but has no completed-summary or Gate 4H verdict authority.

`ncc.coexistence_display` is a completed-only in-memory projection over one integrated result, not another persisted schema or a replacement for either progressive display. It binds the existing topology, application evidence, outcome, cleanup evidence, manifest, composition verdict, historical events, and typed journey; fails closed on identity, digest, lifecycle, report-count, journey, or reducer-support disagreement; and exposes the exact accepted line support independently from its later receiver tail. Its scenario-folio browser is retained as the detailed run report rather than the default operator surface.

`ncc.board_display` adds no evidence reducer or persisted schema. It names one result and supplies the existing validated historical-display snapshot while the event stream grows; only after the formal manifest is terminal does it require and expose the existing completed coexistence projection. `ncc.board_server` serves a minimal fixed-map board at `/` and the detailed completed report at `/report`, accepts GET and HEAD only, and returns an explicit waiting response before the first complete event header. Configured-only links remain neutral, the one mapped line receives only reducer state, IMP lamps reflect attributed report evidence, typed boundary state appears only after completed journey validation, and the only motion is a pulse caused by a newly received direct event.

The board now also accepts the already-supported alternate-path fault and line-loopback terminal result families through their existing completed historical projection. Those results do not acquire an application claim or the coexistence-only detailed report. The change is an adapter choice over validated artifacts, not a new summary, parser, or browser authority.

The only log parser in this slice is `ncc.h316_journey`, a narrow H316 `HI`/`MI` transfer adapter for the established `MSG`, `UDP`, and receive-completion trace grammar. It reassembles literal consecutive host-interface chunks with the same firmware message number and refuses compressed or incomplete word content. `ncc.pdp11_its_journey` uses literal MI packet equality across the IMPs and the established adjacent HI-to-MI containment relation inside each source. It labels the connected host's egress as harness-derived peer delivery, labels H316 transfers as direct trace observations, and leaves both destination-host ingress boundaries unobserved. KA10 `DATAIO` and PDP-11 IMP11-A DMA/packet evidence have named typed construction seams but no speculative universal log parser. A [read-only adapter exercise](experiments/2026-08-31-ncc-message-journey-trace.md) against the existing external `imp11a-telnet-ka10-trace-20260831T131616Z` record recovered exact IMP 62 `HI2` request ingress and repeated exact reply egress transfers; the external run remains outside the repository and is not required by tests. The subsequent [bounded KA10 feasibility pass](experiments/2026-09-01-ka10-host-ingress-grammar.md) stopped before a parser because the existing input trace does not bind a printed `DATAI` value to its receive-assembly width, final valid-bit count, and message identity; the accepted journey also retains no KA10 device trace.
