# DEC IMP11-A device model

**Observed through 2026-08-31:** The PDP-11 now reaches a usable TELNET session on ITS host 106. Exact final run `imp11a-telnet-usable-final-20260831T193000Z` records simulator revision `2722eef4`, `Connection open`, the ITS `TTY 53` greeting and welcome banner, and a remote `:TIME` response with the time, date, and ITS uptime. The last defect was not daemon socket matching: the simulator discarded every returned frame after the guest's four-word leader buffer, asserted `ENDMSG`, and prevented the preserved driver from rearming for the control text. Published simulator revision `2722eef44f68642eaab9f5d4e989ccd26e55e7de` retains surplus input across guest DMA buffers, reports residual `IWC`, and completes only when a buffer fills or the real final marker arrives. The earlier byte-order, header-acceptance, and balanced-RFNM findings remain settled. This note retains the detailed evidence; [workstreams](../workstreams.md) owns current handoff state.

This continues the plan in [PDP-11 Network UNIX as the first heterogeneous host](pdp11-network-unix.md). It records the register-level design and the verification performed so far for the new IMP11-A device.

## Register map

Reconstructed from the DEC IMP11-A technical manual and from the register-level behavior of the SRI/NOSC "imp11a" kernel driver in the preserved Network UNIX V6 source (register addresses, bit positions, and hardware behavior are historical facts about the physical device, not the driver's expression; no driver source is reproduced here).

Fixed base `0172410`, 12 words (`030` octal / 24 bytes), non-autoconfigured:

| Offset | Register | Notes |
|---|---|---|
| 0 | OWC | output word count, two's-complement |
| 2 | SPO | output start address (low 16 bits) |
| 4 | OSTAT | output status |
| 6 | OMAINT | output maintenance |
| 10-16 | (unused) | real hardware does not decode this range |
| 20 | IWC | input word count, two's-complement |
| 22 | SPI | input start address (low 16 bits) |
| 24 | ISTAT | input status |
| 26 | IMAINT | input maintenance |

Two fixed interrupt vectors, `0124` (output) and `0274` (input). These are not the standard DEC `vec, vec+4` pair that Open SIMH's generic multi-vector DIB assignment loop assumes for a device with `vnum > 1`, so the DIB's `vec` field remains `0` and its two interrupt-ack callbacks return the fixed input and output vectors. The focused CPU regression established why callbacks are necessary: writing `int_vec` directly during device reset appeared to work until the generic Unibus DIB rebuild cleared that table, after which the input interrupt vectored through zero.

Status-register bits (shared layout, some read-only in one half): `GO` (start), `RST` (self-clearing reset), `IENAB` (interrupt enable), `XMEM` (2-bit extended address, giving 18-bit Unibus DMA addressing from the 16-bit SPO/SPI plus these bits), `OENDMSG` (output: this buffer ends the message), `WRTENBL` (input: enable receive), `HMASRDY` (input: pulse to tell the peer this host is up), `MASRDY` (input, read-only: peer/IMP reports ready), `ENDMSG` (input, read-only: a full message was received), `DONE` (output, read-only: transfer complete), `TIMOUT` (read-only: transfer timeout, not yet driven by any real fault condition).

## Wire protocol

The device reuses the H316 device family's existing UDP transport (`H316/h316_udp.c`: `udp_create`/`udp_send`/`udp_receive`), unchanged, exactly as the KA10 NCP-mode IMP device (`PDP10/kx10_imp.c`) already does to reach an H316 IMP's host port. This is the same shared component the two-ITS gate depends on, MIT-style licensed with a no-name-in-advertising clause, already vendored into both `ka10-simh` and `open-simh`.

The actual UDP payload is a `UDP_PACKET` struct: `magic` (`"H316"`, `htonl`), `sequence` (`htonl`, per-link monotonic), `count` (`htons`, word count of the data that follows), then `count` data words (`htons` each). The device-level convention layered on top, shared with `h316_hi.c` and `kx10_imp.c`, is that the first data word is a flags word (`PFLG_FINAL` = 1, `PFLG_READY` = 2) and the rest is the actual message content. None of this needed to be invented; it was fully determined by reading the existing shared code before writing anything new.

`h316_udp.c`'s "Connect=" UDP mode means each link behaves like a connected socket: it only accepts datagrams from the exact configured remote host and port. This tripped up the first verification attempt (see below) and is worth remembering for any future test harness against this device.

## Verification performed

Before any guest driver ran against it, the device was verified in isolation: a real CPU-executed bus write (not a debugger register poke, which bypasses the write handler entirely) drives the device correctly, in both directions, using hand-assembled PDP-11 machine code deposited into memory and executed with `step`. (The real `green/unix` guest driver has since run against it too; see [Booting green/unix under this device](#booting-greenunix-under-this-device) below.)

- **Output:** `MOV #imm,@#addr` instructions set SPO/OWC then wrote OSTAT with `GO|OENDMSG|IENAB`. The device read the guest memory word via `Map_ReadW` and transmitted it. The resulting UDP datagram was captured and decoded by hand: magic, sequence (0, first packet on the link), count (2), and both data words (flags `3`, and the exact guest memory content) all matched exactly.
- **Input:** a hand-built `UDP_PACKET` (flags `PFLG_FINAL`, two data words) was sent to the device's attached port from a source bound to the exact configured remote port (required by the "Connect=" filtering above). Guest instructions then wrote SPI/IWC/ISTAT with `GO|WRTENBL|IENAB`. The device's synchronous re-check on that write (not a scheduled poll) picked up the already-queued datagram immediately, `Map_WriteW`'d both data words into the exact requested guest memory addresses, and set ISTAT to `IENAB|ENDMSG`.

The build also passes Open SIMH's own `RegisterSanityCheck` self-test.

## Open questions for guest testing

Updated after starting the real daemon against the live device; see [Starting the NCP daemon](#starting-the-ncp-daemon) below for how each of these was actually resolved or narrowed.

- Whether the guest ever chains multiple output buffers into one message: not observed in any live run so far. Every guest-originated send seen so far, including the connection control and usable TELNET exchange, is an `OENDMSG`-terminated buffer; a larger TELNET/FTP transfer may still chain and remains untested.
- The short or partial input contract is now closed for the exercised receive path. The adapter increments `IWC` as a residual count, retains surplus frame words when a guest buffer fills, continues a partial non-final buffer without interrupting, and asserts `ENDMSG` only when the final data or empty-final marker is consumed. The focused regression and usable TELNET run both exercise that behavior.
- `TIMOUT` and the general error-summary bit are defined but nothing yet drives them; still untested.
- `DEBTAB` (`SET IMP DEBUG=REG;INT;PKT`) is now implemented, and is what made the findings below observable.

## V6 base: reproducing the pristine root filesystem

The official [SIMH UNIX V6 software kit](https://sourceforge.net/projects/simh/files/Software%20Kits/UNIX%20v6%20for%20the%20PDP-11./) (Caldera/Ancient-UNIX licensed) boots to a login prompt on this same Open SIMH build unmodified: `SET CPU 11/34`, `SET CPU 128K`, `SET CPU NOAUTOCONFIG`, attach its four RK05 images, `BOOT RK0`, then `unix` at the `@` prompt. This confirms the IMP11-A changes above do not disturb the baseline PDP-11 simulator.

Reproducing that same root/source/doc filesystem set from the raw historical distribution tape (rather than the prebuilt kit) turned out to need a different method than the one documented method assumes. The [`eblanton/unix-v6-install`](https://github.com/eblanton/unix-v6-install) reference (`94df669009311ce0e693aa326142732f77796813`, no declared license, used here only as a methodology reference, not copied into any repository) drives this via an in-simulator `tmrk` meta-command that does not exist in Open SIMH; every attempt using it hangs indefinitely on an unmatched `expect "="`.

Its own tape-processing tool (`v6enb`'s `enblock`, converting a raw historical tape image into SIMH's `.tap` container format) still works once its 2001-era C is coaxed past current clang's default-error implicit-function-declaration checks (`-Wno-error=implicit-function-declaration -Wno-error=implicit-int`). The resulting `.tap` file is exactly 12,100 fixed 512-byte tape records plus a tape mark: the first 100 are a raw bootstrap area, then three 4,000-record filesystems back to back (root at tape offset 100, `/usr/source` at 4,100, `/usr/doc` at 8,100). Because a SIMH `.tap` record is just a length-prefixed byte range, those three filesystems can be extracted directly, at the host level, straight into zeroed RK05-sized target files, with no PDP-11 execution involved at all: [`scripts/research/extract-v6-tape.py`](../../scripts/research/extract-v6-tape.py). That reproduced root filesystem boots and logs in identically to the official kit (`rkunix`, root, no password) with the historically correct embedded clock (`Fri Oct 10 12:29:44 EDT 1975`).

This matters here because it is the same technique the remaining work depends on: getting the prelinked `green`/`green47` kernels and the NOSC NCP daemon and applications onto a filesystem this simulator can boot does not require rebuilding anything from source (they are already built), only correctly placing existing bytes.

## Injecting files directly into a V6 filesystem image

Getting the prelinked `green/unix` kernel and the NCP daemon onto a filesystem needed a way to place already-built binaries directly, since there is no source to compile in place and no working in-simulator tape-write path. [`scripts/research/v6fs.py`](../../scripts/research/v6fs.py) implements exactly the on-disk structures in `ino.h`/`filsys.h`: superblock free-list allocation (including the classic V6 trick where the block about to be handed out is first read as the next free-list chunk), inode allocation by linear scan for `i_mode == 0`, small (direct-block) and large (single-indirect) file writes, and directory-entry insertion. It has a small CLI (`mkdir`, `put-file`, `mknod`, `lookup`) as well as being importable.

The first version had a real bug, caught by testing against a live boot rather than only re-reading the bytes with the same tool that wrote them: reusing a deleted (`ino == 0`) directory slot beyond the directory's current logical size wrote valid bytes that the kernel's own directory scan, bounded by the inode's `size` field, never reached. A file placed this way was invisible to `ls`/`open` even though it was genuinely on disk. Fixed by tracking size explicitly and only ever treating a slot as reusable when it falls within `[0, size)`; anything past that must grow `size` by exactly one 16-byte entry, whether or not it also requires a new block.

## Booting `green/unix` under this device

Two more facts had to be pinned down before a boot attempt meant anything, both by disassembling the actual `green/unix` a.out binary rather than guessing, since NOSC's own kernel-config table was not preserved in the archive:

- **`/dev/ncpkernel`'s major number.** `cdevsw` (found in the binary's data segment via its own symbol table entry) is an array of `{open, close, read, write, sgtty}` function-pointer quintuples. Scanning it for the address of `_ncpopen` (the daemon-facing entry point in `ncpio.c`, not the lower-level `_impopen`/`_impread` internal to the driver) lands at index 25, i.e. major **5** — confirming the number already recorded in [pdp11-network-unix.md](pdp11-network-unix.md) independently.
- **Root and swap devices.** The `_rootdev`/`_swapdev` data symbols decode directly to `(1,0)` and `(1,1)`: `bdevsw` entry 1 is the RL driver (`_rlopen` at that slot), so root and swap are both on RL, unit 0 and unit 1 respectively.

Booting the resulting image over Open SIMH's `RK0` failed immediately (`panic: iinit`, `err on dev 1/0`) because attaching the very same bytes as `RK0` presents major 0, not the major-1 RL device the kernel expects — a software-level dispatch mismatch, not a data problem. Attaching as `RL0` instead got further but failed silently at the boot-ROM prompt (`@`) for every filename, including the already-known-good `rkunix`: the disk content's boot block (byte-identical to the RK-formatted image) contains RK-specific low-level disk I/O, which does not work when the CPU is executing it against an RL-attached device. The fix, taken directly from the `eblanton/unix-v6-install` `pristine-rl` script's own logic (copying an RL-native boot block over before use), was to overwrite block 0 with the boot block from the real RL02 reference image (Tim Shoppa's `unix_v6.rl02`, TUHS-hosted, methodology reference only). That RL bootstrap prompts with `!`, not `@`. With that block 0 and a second RL01 unit attached for swap (`err on dev 1/1` without one — `swapdev`, not root, once root itself was reachable), `green` boots cleanly to `login:` and root logs in.

The confirmed-present, confirmed-correct result on a live boot: `/dev/ncpkernel` (`crw-rw-rw- root 5, 0`), `/green` (42,988 bytes, matching the source file exactly), and `/usr/net/etc/Largedaemon` (17,648 bytes, matching exactly). This is the actual NOSC-built kernel — not a synthetic test program — reaching a shell with the new IMP11-A device attached, root and swap on RL, and the NCP daemon binary in place at the path its own `smalldaemon` launcher (recovered by reading its embedded strings) expects. [`scripts/research/boot-green-with-imp.py`](../../scripts/research/boot-green-with-imp.py) reproduces this boot and check.

## Starting the NCP daemon

`/usr/net/etc/smalldaemon` (954 bytes, matching the archive's copy exactly) was already present on the working root image alongside `Largedaemon`, though not yet run. Starting it — `open("/dev/ncpkernel", 2)` then `execv` into `Largedaemon` on that same file descriptor, per its own source — drives `ncpopen()` → `impopen()` → `imp_init()` in the real preserved driver (`ncpk/drivers/imp11a.c`, `ncpk/drivers/impio.c` in the pdp11/network-unix-v6 tree), the exact register sequence this device model exists to answer. Reaching that required adding the `DEBTAB` support flagged as missing above (`SET IMP DEBUG=REG;INT;PKT`, plus `SET DEBUG -n <file>` for the destination), reusing the same `DBG_REG`/`DBG_INT` idiom as the sibling `pdp11_dup.c`. [`scripts/research/start-daemon-with-imp.py`](../../scripts/research/start-daemon-with-imp.py) reproduces the boot-and-start; [`scripts/research/udp-test-peer.py`](../../scripts/research/udp-test-peer.py) is the minimal external peer used below.

**A real device bug, found only by running the real driver.** The first attempt hung: `smalldaemon` opened cleanly and the console printed `IMP:Reset`, but the daemon never progressed past it, and `IMP:Init` never printed. The debug trace showed why: `imp_rd`'s `ISTAT` case OR'd `IMP_MASRDY` into every read whenever the device was attached (`imp_link >= 0`), regardless of whether any peer had ever actually signaled ready. The real driver's `imp_init()` does exactly `while (IMPADDR->istat & imasrdy) sleep(&lbolt, 0);`, intending to wait until a peer's READY is seen — with the bug, that condition was permanently true from the moment of attachment, so the real driver spun forever, before ever enabling interrupts or sending anything, with or without a peer on the other end. This is why the isolated bus-write verification recorded above never caught it: that test hand-poked `GO|WRTENBL` directly and never ran the driver's own `imp_init()`, so it never read `ISTAT` in a state where MASRDY needed to still be zero. Fixed by dropping the on-attach synthesis; `ISTAT` now reports exactly `imp_istat`, and MASRDY is set or cleared only by `imp_check_input()` from a real received `PFLG_READY`, matching the register map's own "peer/IMP reports ready" description.

**With the fix, the real driver's startup sequence matches the reconstructed source register-for-register**, observed over `SET IMP DEBUG`: `imp_reset()`'s explicit software `RST`-set-then-clear on both halves (the driver does not rely on hardware self-clear, even though the real vector/CSR behavior is self-clearing); one `HMASRDY` pulse from `set_HMR()`, correctly producing one outbound READY-flagged keepalive datagram; `IENAB` enabled on both halves; exactly three startup NOPs sent from `impopen()`'s init loop, each a single 2-word `OENDMSG`-terminated buffer (`OWC`/`SPO`/`GO` written once per NOP, no buffer chaining for a message this size); `IMP:Init` printed; and the first input leader read armed (`SPI`/`IWC`/`ISTAT` with `GO|WRTENBL`). All of this had never been exercised by real guest code before this session.

**The daemon keeps talking after startup.** Once running, `Largedaemon` continues sending identically-shaped 2-word NOP/keepalive probes on its own periodic timer, independent of whether anything ever answers — a real, previously undocumented steady-state behavior worth expecting once the two-IMP topology is wired up, not just the three one-time startup NOPs.

**Proving delivery needed a genuine external peer, and two test-setup mistakes had to be found and corrected first**, both worth recording for whoever runs this next:

- Attaching with equal local and remote ports (e.g. `9000::9000`) makes the device receive its own transmissions back as if a perfectly-echoing peer were attached — every self-sent packet loops straight back in. This produced a long, misleading run of what looked like protocol activity before the mechanism was understood.
- `ATTACH IMP <port>:localhost:<port>` resolves `localhost` to IPv6 `::1` on the tested machine, `lsof` confirmed. An external test peer bound to IPv4 `127.0.0.1` on the matching port never sees any of it, and outbound sends toward that unreachable IPv6 endpoint get OS-level connection-refused errors that Open SIMH's TMXR layer reports, confusingly, as `tmxr_put_packet_ln() failed with error Console Telnet connection lost`, once per further send attempt. Using an explicit `127.0.0.1` in the attach string forces IPv4 and fixes this. [`docs/runbook.md`](../../docs/runbook.md) already pins every configured peer in this project to IPv4 loopback for exactly this class of mismatch; this is the same gotcha, independently rediscovered against this device.

With both corrected, a minimal external Python process (not a peer NCP/IMP implementation — just enough of the `h316_udp.c` wire format to send a periodic READY-flagged keepalive and log what it receives) exchanged real, independently observed traffic with the guest: 30 datagrams delivered guest-to-peer over the run, decoded outside the simulator entirely and matching the debug trace's own `OWC`/flags exactly, and the guest's `MASRDY` bit now correctly tracked the peer's real `PFLG_READY` signal through `imp_check_input()` rather than the removed synthesis. The peer in this run only ever sent flag-only (zero-data) keepalives, so the input side never received a real multi-word message and never fired an input interrupt; the short/partial-input-completion contract and `TIMOUT`/error-summary handling are consequently still untested; a real peer that answers with actual message content is needed for that, which the two-IMP topology step will naturally provide.

**One anomaly remains unexplained.** The guest console prints `IMP: Phantom Out Int` — the driver's own message for an output interrupt arriving while its software bookkeeping (`impotab.d_active`) already reads zero — exactly once per run, immediately after the three startup NOPs complete. It reproduced identically in the self-loopback run and in the corrected external-peer run, so it is not an artifact of either test-setup mistake above, but its root cause has not been isolated (a candidate: something about how the three back-to-back `impstrat`/`iowait` completions interact with this device's fixed 100-tick output-completion scheduling). It has had no observed adverse effect — boot and the daemon both continue normally — so it is recorded here rather than chased further this session.

The debug-tracing and `ISTAT` fix described above are published on [`brfid/imp11a-simh`](https://github.com/brfid/imp11a-simh)'s `imp11a-device` branch (`a56c68ed`), on top of the branch's existing device commit; see [Location](#location) above. The run logs (console transcript, register/interrupt/packet debug trace, and the external peer's independent capture) are immutable per-run evidence directories under the lab's `results/`, per [`docs/runbook.md`](../../docs/runbook.md); they are not committed to this repository, consistent with [`NOTICE.md`](../../NOTICE.md).

## Wiring into the two-IMP topology

The two-IMP fabric already proven for the two-ITS smoke — IMP 6 and IMP 62 joined by `mi1`, each with a host on `hi2` — needed no PDP-11-specific change at all. [`config/imp/its-pair/imp6.simh`](../../config/imp/its-pair/imp6.simh), [`config/imp/its-pair/imp62.simh`](../../config/imp/its-pair/imp62.simh), and [`config/hosts/its106-pair.simh`](../../config/hosts/its106-pair.simh) were reused byte-for-byte: ITS host 106 stayed on IMP 6's `hi2` exactly as in the existing pair, and the `green/unix` guest took IMP 62's `hi2` in place of the second ITS host, attaching over the identical H316 UDP transport and flag-word convention any host uses there. [`scripts/research/two-imp-its-with-pdp11.py`](../../scripts/research/two-imp-its-with-pdp11.py) drives all four processes (IMP 6, IMP 62, ITS host 106, and the PDP-11 guest) and reproduces the run below; it is a manual smoke check, not the formal `two-its-controller.py` — no port lease, no run manifest, informal readiness checks against the same watchdog-light and console-banner text [Gate 4](../test-plan.md) uses formally.

Both H316s reached modem-up (`077400`) and host-link-up (`075400`) watchdog lights, ITS host 106 booted cleanly to its system-console banner and a login prompt exactly as it does in the existing two-ITS smoke, and the PDP-11 guest attached to IMP 62's `hi2` and started `smalldaemon` without incident. ITS logged one benign `IMP: Interface-reset msg` (the same telemetry line [the test plan](../test-plan.md) already documents as expected, not an error) and was otherwise undisturbed for the full run; its media was booted from a fresh per-run copy, and the shared prepared source was confirmed unmodified afterward.

**This was the first time the device received real, substantive, multi-word traffic from a genuine external network, but the contemporary interpretation of its short completions was wrong.** The guest's four-word leader buffer filled and the guest kept running, which initially looked like successful partial-message handling. Later exact socket tracing proved that the device discarded every surplus word, replaced `IWC` with the negative delivered count, and asserted `ENDMSG`; the driver therefore treated the leader as the complete message and never rearmed for its control text. The receive-continuation section below supersedes that interpretation with the focused contract test and usable application proof. `TIMOUT`, the error-summary bit, and output buffer chaining remain untested.

**A new, real, only-partially-explained observation:** `Largedaemon` logs `no link:  1   0  17   7   0` once per received message (`ncpd/hr_proc.c`'s `hr_data()`, printed when a regular host-to-host message arrives for a host+link with no matching open connection). Cross-referencing IMP 62's own `hi2`-debug log (already enabled in the reused config) for the same window shows the likely source: `HnFOUT` (host output) events emitting a real 2-word message (`002000 000000`, octal, actual content words rather than a bare flags-word keepalive) toward the PDP-11's port on its own initiative, distinct from and in addition to the ordinary 1-word `PFLG_READY`/`PFLG_FINAL` ready-bit pulses (`HnUNXP`/`HnRDY`, already correctly handled by this device's existing `count == 1` keepalive short-circuit). The most likely explanation is that this is standard 1822 host-interface traffic — plausibly routing or interface-status information the IMP subnet delivers to any attached host — that a real IMP11-A's own hardware would most likely classify and absorb rather than hand to the host as ordinary message content the way this device's current, deliberately minimal wire model does; this device has no concept yet of separating 1822 leader/control content from host-addressed application data, only the `PFLG_READY`/`PFLG_FINAL` flag word already borrowed from the shared transport. This is recorded as a well-reasoned hypothesis, not a confirmed root cause — nailing it down further would mean reading the BBN 1822 specification and the DEC IMP11-A manual's leader-format sections directly, which has not been done yet this session, per the project's own standing guidance to consult primary historical documentation before treating an investigation as stalled rather than guess further.

An application-level proof (guest TELNET to ITS host 106, per the original plan) needed a TELNET client first: the preserved archive has no prelinked, ready-to-run one. `Largedaemon` and `smalldaemon` were prelinked and needed no build step; `ncpp/tel-u/telnet.c` and its companions are source only, and `ncpp/tel-s/svrtel.o` is an unlinked relocatable object, not an executable — a scan of every file in the preserved tree found exactly two ready-to-run, application-facing network binaries, both already in use. Building one from that source is recorded below, and attempting the connection with it after.

## Building a guest TELNET client from source

[`scripts/research/build-guest-telnet.py`](../../scripts/research/build-guest-telnet.py) reproduces this. It builds `ncpp/tel-u/telnet.c` and its companion `usrtelnetin.c` (the process `netopen()` forks to read the network and write the terminal — a real two-way session needs it too) entirely with V6's own `cc`, in-guest, against the pinned [`pdp11/network-unix-v6`](https://github.com/pdp11/network-unix-v6) checkout (now pinned in [`pins/sources.lock.toml`](../../pins/sources.lock.toml) rather than reference-only, since this is now a real build dependency). This validates the plan's stated preference for the in-guest toolchain over a cross-toolchain — V6 `cc` had no trouble with either file — but getting a clean compile needed three archive-fidelity gaps bridged first, none of them by inventing new values:

- **`ncpp/tel-u/telnet.c` itself is corrupt in the checked-out tree**: same byte length family as real source but entirely zero-filled. `ncpp/tel-u/telnet.c.org`, 9 bytes smaller, is intact and is what the build script actually compiles. This is a real preservation defect in the archive, not something this project did to it — `git show` against the pinned revision confirms the zero-filled content is already what is committed upstream.
- **Two headers `telnet.c.org` includes by absolute path don't exist under those names**: `/h/net/mkcharset.h` and `/h/net/openparms.h`. `h/net/mcharset.h` and `h/net/open.h` are, respectively, byte-for-byte the same content under different preservation-copy filenames — confirmed by reading their defined symbols (`maptab`, `definetab`, `stringtab`, ... for the first; `struct openparams` with exactly the fields `telnet.c.org` references for the second) against what the source actually uses, not by name similarity alone.
- **`telnet.c.org` and `usrtelnetin.c` reference TELNET protocol constants in lowercase** (`tel_iac`, `otel_echo`, `to_echo`, ...); the preserved `h/net/telnet.h` defines only the uppercase forms (`TEL_IAC`, `oTEL_ECho`, `TO_ECHO`, ...) — a real historical header/source revision mismatch, not a corruption. The build script's staged copy of `telnet.h` appends a lowercase-alias block (`#define tel_iac TEL_IAC`, and so on for every symbol either file references), aliasing to the existing values rather than restating them.

Two more findings, neither about the source itself:

- **A stray `*/` inside a first attempt at writing that alias block's own explanatory comment silently closed the C comment early**, turning the rest of the comment into garbage tokens the compiler dutifully reported as syntax errors on the `#include` line above (V6 `cc`'s error reporting doesn't track line numbers inside an included file, so every error inside `telnet.h` gets attributed to whichever `#include` line pulled it in — worth remembering for any future header edit here).
- **`/dev/net/anyhost`** — the device NCP applications open to request a connection by host number (`struct openparams` in `net/open.h`; `netopen()` in `ncpk/nopcls.c`) — is not just any character-special node. Disassembling the actual running `green` kernel's `open1()` (via its own a.out symbol table, the same technique already used to find `/dev/ncpkernel`'s major) showed the dispatch to the kernel's `netopen()` is gated on the target inode's device-number *major* byte reading as a negative signed byte — octal `0200`–`0376`. A small major like the ncpkernel's `5` falls through to the ordinary `cdevsw` path instead, where it collides with the already-open ncpkernel device and fails with `ENCP2`; the guest telnet client has no way to show that distinctly and just prints "`Host is Unavailable`" either way, which is what the first attempt (major `5`) did. `--anyhost-major`/`--anyhost-minor` default to `0200`/`0106` (octal 106, matching [the test plan](../test-plan.md)'s own host-106 convention; minor is advisory only, since a real connect always passes an explicit `-h`).

One operational gotcha, not specific to this device: **force-closing the simulator's pexpect session right after `quit` can silently lose a just-compiled `a.out`.** SIMH's writes to an attached disk-image file are not guaranteed flushed to the host file until the simulator process actually exits on its own; the first attempt at scripting this force-closed a few hundred milliseconds after sending `quit` and the compiled binary was simply gone on the next boot. The build script waits for a clean process exit (`pexpect.EOF`) instead, falling back to a forced close only if that hangs.

With all of that, `cc -O -n -x telnet.c` and the same for `usrtelnetin.c` both compile clean, no cross-toolchain needed; the script installs both to `/usr/bin` mode `1755` and creates `/dev/net/anyhost`, all on a copy of the caller-supplied root image.

## Attempting the guest TELNET connection

[`scripts/research/two-imp-its-pdp11-telnet.py`](../../scripts/research/two-imp-its-pdp11-telnet.py) wires a root image built by the script above into the same two-IMP topology proven above, starts `smalldaemon`, and runs `/usr/bin/telnet - -h 106` — the client's own argv-triggered connect syntax (see the client's own `-h` option, which takes the host number in octal, matching `number()`'s own unconditional octal parse).

**The daemon does send a real RFC/ICP pair.** The PDP-11's own `IMP DEBUG=REG;INT;PKT` trace shows two genuine (non-keepalive) output transfers right after `Attempting Connection` prints: a 2-word buffer and a 5-word buffer, both `OENDMSG`-terminated. Cross-referencing IMP 62's `hi2` debug log (already enabled in the reused config) for the same window confirms both arrived, byte-for-byte, as two real `message received` events distinct from the routine keepalive traffic — genuine new NCP application-layer traffic leaving the guest, further than this project has gotten before.

**But the connection does not complete.** No corresponding new activity shows up on IMP 6's `hi2` log (ITS's side) anywhere near that time — its last `hi2` activity in the whole run is from ITS's own early self-announcement, tens of millions of ticks before the guest even starts `smalldaemon` — and ITS's own console never reacts: no incoming-connection service job, nothing. The guest's own `telnet` eventually reports "`Host is Unavailable`" (its default timeout of 30s applies since the connect syntax used above doesn't override `-t`).

**A second daemon log line appeared during this run but is very likely the same already-recorded phenomenon, not a new bug this attempt caused.** `Largedaemon` also logs `ir_reglr: bad data link:  1   0  17   1   0` once during this run (`ncpd/ir_proc.c`'s `ir_reglr()`, for a received leader whose link field is 1 or greater than 71 — both illegal). Decoding the same five logged bytes as `kread.h`'s `kr_rcv` struct (`kr_op`, `krr_type`, `krr_host`, `krr_link`, `krr_sbty`) gives `krr_host=017` octal in both this message and every recurring background `no link:  1   0  17   7   0` line already present in every run today, before this attempt ever starts — the same fixed, seemingly-content-free `017` field, consistent with the already-recorded, not-yet-confirmed hypothesis that this device model is delivering unfiltered 1822 leader/control content to the guest as if it were application data. That noise is continuous background static across every run so far, uncorrelated with this attempt's timing, and is very unlikely to be why ITS never answered.

The more likely explanation, not yet isolated, is a relay or routing gap between IMP 62 and IMP 6 for this specific traffic — genuinely new NCP host-to-host content is not the same class of traffic as the 1822 status/keepalive exchange this same two-IMP path has already proven end to end. Two things worth trying before assuming a real bug: a longer `--daemon-settle` and a longer wait before sending the RFC (routing-table convergence timing between the two IMPs for this traffic was never isolated from a genuine relay defect this session), and checking IMP 62's `MI1` trace for whatever it did or didn't forward toward IMP 6 in the same window (not yet read closely — the `HI2` side was the only side inspected before this was set aside).

## Isolating the IMP 62 → IMP 6 relay gap (2026-08-30, continued)

Re-examined the already-captured evidence from the last recorded attempt (`imp11a-telnet-attempt-20260830T220131Z` in the lab's `results/`) rather than rerunning the experiment, since both open follow-ups from the previous session are answerable from what that run already recorded.

**Routing-convergence timing is ruled out.** IMP 62's own `MI1` debug log carries continuous, steady-state routing-table and keepalive exchange with IMP 6 for the entire run — including the exact tick window (`453009000`–`453011000` on IMP 62's own clock) where its `HI2` log shows the guest's two output transfers arriving. There is no gap, burst, or any other change in that traffic correlated with the arrival: the link was fully converged well before, during, and after. A longer `--daemon-settle` would not be expected to change the outcome and does not need to be tried before treating this as a real relay/interpretation gap rather than a timing artifact.

**The device model and the guest's own IMP11-A kernel driver are both confirmed clean.** Reading the new device (`pdp11_imp.c`, this project's own code) and the preserved guest kernel driver it talks to (`ncpk/drivers/imp11a.c` in the pinned `network-unix-v6` checkout) shows both sides are transparent word-for-word DMA-to-wire pipes: neither inspects or constructs any 1822 leader content. `imp11a.c`'s output routine only ever drains whatever buffer the kernel's generic network-buffer code queued for it — this also independently confirms the `IMP: Phantom Out Int` message from [Wiring into the two-IMP topology](#wiring-into-the-two-imp-topology) above is this driver's own unexpected-output-interrupt printf, not anything device-model-specific. So the two transfers reaching IMP 62's `HI2` are exactly the bytes the guest kernel intended to send, unmodified by anything this project wrote.

**`hi2 convert` is a no-op for messages this small and is not implicated.** The H316 host-interface source's long-to-short leader converter (`h316_hi.c`, in the pinned `h316-simh` checkout) only acts on a message of 7 or more words carrying a specific new-format flag bit; both observed transfers (2 and up to 3 words after the flags word is stripped) are well under that threshold, so the converter's own early return hands them to the IMP's short-leader path completely unchanged. Toggling `convert`/`noconvert` on this host line would not change anything for a message this shape.

**Byte-level reconstruction shows the leader guest-side is well-formed and correctly addressed.** The generic kernel routine that builds every host-interface leader (`sndnetbytes()` in `ncpk/kerbuf.c`, shared by every driver, not IMP11-A-specific) writes a fixed 9-byte, even-padded leader — type, destination host, link, subtype, two pad bytes, byte-size, and a byte-swapped content-byte-count — immediately followed by any message content, all in one buffer when it fits. Decoding the two captured transfers against that exact byte layout (confirmed against the transfer's own field order, not guessed):

- The 2-word transfer decodes to type = `4` (NOP), host = `0`. This is `Largedaemon`'s already-documented periodic background NOP keepalive (see [Starting the NCP daemon](#starting-the-ncp-daemon) above) landing at the same moment by coincidence, not part of the connection attempt — the previous session's "RFC/ICP pair" framing over-attributed this one to the guest telnet client.
- The 5-word transfer decodes to type = `0` (regular), host = `70` decimal = octal `106` — an exact match for the ITS host number the client was given (`telnet - -h 106`, parsed in octal) — link = `0` (the NCP control link, correct for a connection-setup message), byte-size = `8` (forced for link 0 by the same routine), and a content length of exactly 1 byte, whose value is `12` decimal. This is the guest's actual, single, correctly-addressed NCP connection-setup message; everything about its leader is internally consistent and points at the right destination.

**Checked two primary sources rather than guessing further.** The [DEC IMP11-A manual](https://bitsavers.org/pdf/dec/unibus/IMP11-A_PDP-11_Host_to_IMP_Interface_Feb1975.pdf) (OCR text via its Internet Archive mirror, since the direct bitsavers link now 404s) confirms the hardware itself contributes no leader framing at all — it describes only a generic bit-serial word transfer, citing BBN Report 1822 for message content, meaning the *entire* leader, old or new, is the host software's responsibility, consistent with `pdp11_imp.c` and `imp11a.c` both being confirmed transparent pipes above. Secondary sourcing on BBN 1822's own history (not the primary report text itself, which was not accessible this session) narrows the "old leader" this host predates: it was 32 bits (2 words) with a 2-bit host field and 6-bit IMP field, used from 1970 until the 96-bit "long leader" replaced it around the end of 1975 — and `h316_hi.c`'s own `OLEADER_*`/`NLEADER_*` split exists specifically to support both as real historical formats, not as a defensive fallback.

That raises a real problem with the decode above: a 2-bit host field cannot hold the value `70` (host 106 octal) the 5-word transfer's leader decodes to. `imp11a.c`'s own header carries edits as late as "KLH 4/79" — after the long-leader transition — so the driver actually shipped in this preserved tree may already assume wider, NCP-global host numbering (matching every other convention this project uses) rather than the original 2-bit per-IMP port field, packed into a leader shorter than the standard 96-bit/6-word long-leader layout `h316_hi.c`'s converter looks for. If so, the guest is sending a real, internally-consistent, SRI/NOSC-specific leader convention that is simply narrower than either format the pinned H316 firmware's converter recognizes — a genuine revision mismatch between two independently-recovered historical artifacts, not a bug in this project's own code. This is recorded as a well-reasoned hypothesis, not a confirmed root cause: it would take either the full BBN Report 1822 text (not reachable this session — only secondary summaries of it were) or disassembling the loaded IMP firmware (`impcode.simh`, an opaque octal load, not project source) around its message-type dispatch to confirm which exact leader shape it accepts.

**Superseded below.** The full BBN Report 1822 text turned out to be reachable after all (a better OCR mirror), and comparing this leader byte-for-byte against a *proven-working* implementation's own source — not just the spec — overturns this hypothesis. See [The real root cause: an RFNM bookkeeping deadlock, not a leader or transport problem](#the-real-root-cause-an-rfnm-bookkeeping-deadlock-not-a-leader-or-transport-problem) below.

## The real root cause: an RFNM bookkeeping deadlock, not a leader or transport problem (2026-08-30, continued)

Found the actual BBN Report 1822 (January 1976) OCR'd in full at the Internet Archive (`archive.org/stream/bitsavers_bbnimpBBN1_8769843/BBN1822_Jan1976_djvu.txt`, fetched raw rather than through a summarizer so the exact bit tables could be read directly) and Appendix A's old-style leader diagram — Priority/ForIMP/Trace/Octal flags in bits 1-4, message type in bits 5-8, a **2-bit** destination-host field in bits 9-10, a 6-bit destination-IMP field in bits 11-16, message-id in bits 17-28, sub-type in bits 29-32 — confirming the previous section's reading of the spec was accurate. But the pinned `arpanet-in-a-box` firmware itself turns out to predate this document by years: its own README describes it as running "their original firmware" for a recreation "circa 1972-73" — before the mid-1973 link/message-id field change the report itself notes, and years before the late-1975 long-leader introduction the previous section reasoned from. Appendix A's 2-bit host field was never a live constraint for this exact firmware to begin with.

That reframed the right ground truth as *this project's own already-proven-working NCP implementation*, not the abstract spec. `linux-ncp` (the pinned diagnostic NCP that `smoke-router`/`smoke-mixed` already pass against this same firmware) builds its leader in `src/ncp.c`'s `send_imp()`: four bytes — `flags<<4|type`, destination host as a **full byte**, link as a full byte, `id<<4|subtype` — content immediately follows, no destination-IMP field, no byte-size/byte-count fields. Comparing field-by-field, the guest's captured 5-word leader is *identical in shape* to this working format for its first four bytes: type `0`, host `70` (= octal `106`), link `0`, subtype `0`. The leader was never the problem; the earlier "revision mismatch" hypothesis is retracted.

**What the 5-word message actually is: not the RFC.** The preserved NOSC daemon source (`ncpd/` in the pinned `network-unix-v6` checkout) has its own shared 9-byte leader struct (`ncpd/leader.h`: `l_type, l_host, l_link, l_sbty, l_fill1, l_bysz, l_bycnt, l_fill2`, then data) — the same shape the previous section decoded, confirming that decode was reading the right struct, just misidentifying which daemon routine built it. `ncpd/send_pro.c`'s `mak_ldr()` zero-fills that struct, sets `l_host = host` and `l_bysz = 8` — exactly matching the captured bytes field-for-field, including the swabbed `l_bycnt` encoding a content length of exactly 1 byte. A content length of 1 rules out a real RFC: `ncpd/send_pro.c`'s actual RFC-sending routine, `hw_rfc()`, always queues *10* content bytes (a 1-byte opcode plus 8 zero-padded socket-number bytes it copies via `hw_s2b()`, per `ncpd/hhi.h`'s `hhi_rts`/`hhi_str` opcodes). The single content byte the guest actually sent, decimal `12`, is `hhi_rst` in that same header — this is `ncpd/send_pro.c`'s `chk_host()` sending a defensive **RST**, not a connection request at all.

**Why the real RFC never follows it.** `chk_host()` runs unconditionally at the start of every outgoing connection attempt (`ncpd/kr_dcode.c`'s `kr_ouicp()`, the function `netopen()`'s kernel request reaches in the daemon, calls it and then proceeds regardless of its result — it isn't a gate). If the destination host isn't already marked up, `chk_host()` sends this RST via `qup_pro()` + an immediate `send_pro()` call — and `send_pro()`, right after building and transmitting it, sets the host's bit in `rfnm_bm` (`ncpd/send_pro.c`, "set host's rfnm bit in rfnm_bm"). `kr_ouicp()` then continues synchronously into `so_uinit()` → `hw_rfc()`, which queues the *real* RFC via `qup_pro()` but never calls `send_pro()` itself. The next time anything tries to flush that queue, `send_pro()`'s own first line is `if (bit_on(&rfnm_bm[0],host)) return;` — and the bit the RST's own send just set is still there, so the real RFC sits queued and unsent. The only place that bit gets cleared is `ncpd/ir_proc.c`'s `ir_re_x()`, triggered by an incoming *kernel/IMP-level* retransmission-failure notification for that host — not a self-contained software timer. `x_retries` is `1`, so even if that notification ever arrived, the very first one exhausts retries and calls `h_dead()`, which flushes the queue rather than retrying — the RFC would be discarded, not sent, even in the best case.

**Confirmed empirically, not just by reading.** Reran [`scripts/research/two-imp-its-pdp11-telnet.py`](../../scripts/research/two-imp-its-pdp11-telnet.py) against the same topology and the same already-built telnet image, extending `--telnet-settle` from 25s to 150s (six times longer) to see whether anything eventually unsticks. It didn't: the PDP-11's own debug trace shows exactly one non-keepalive output for the entire 150-second window — the same 5-word RST, at a new tick but byte-identical in shape — and no `ir_re_x`/`h_dead`-related console output ever appears. This directly confirms the deadlock is structural, not a matter of insufficient wait time, and independently corroborates the source-level tracing above: this project's own H316 transport/device C code (`h316_hi.c`, `h316_imp.c`) has no "retransmission failed" or "incomplete transmission" concept anywhere in it either, so there is no evident mechanism in this environment that would ever clear `rfnm_bm` for a silent destination.

**Bottom line:** the guest's 1822-level leader and this project's IMP fabric were never the problem — they're both confirmed working correctly, byte-for-byte. The blocker is a real bookkeeping interaction inside the preserved 1970s NCP daemon itself: its own defensive "reset the host if we don't know it's up" step, run unconditionally before every connection attempt, consumes the one-message-in-flight slot the real RFC needs, and nothing in this environment generates the notification that would free it up again. This is a genuine period-software behavior (or an artifact of never having deployed this exact daemon against a host it had zero prior contact with), not an artifact of anything this project built. Fixing it for real would mean either patching the preserved daemon source (a deliberate call about modifying historical code, not one to make unilaterally) or finding some other way to seed `h_up_bm`/avoid the RST-before-RFC ordering — recorded here as the next decision point rather than acted on.

## A workaround tried first: having ITS dial the guest before the guest dials ITS (2026-08-30, continued)

Before touching the preserved daemon source, tried avoiding the deadlock instead: if `h_up_bm` only needs a message *received* from host 106 to be set (`ncpd/hstat.c`'s `hs_alive()`, called from every `hr_*` receive handler in `ncpd/hr_proc.c`), then having ITS contact the guest first — genuinely, not simulated — should make `chk_host()` skip the RST entirely on the guest's own later connect attempt. This has real historical fidelity: it is exactly the kind of operator-driven "introduce two hosts that have never talked" action a 1970s site could plausibly have needed, not a synthetic shortcut.

[`scripts/research/its-speaks-first-then-pdp11-telnet.py`](../../scripts/research/its-speaks-first-then-pdp11-telnet.py) drives ITS host 106's own console interactively (boot, DDT, `:login db`, then its `UT` program dialing host `176` — the network address IMP 62's `hi2` has carried since the `its176-pair.simh` ITS occupied it; see [`docs/test-plan.md`](../test-plan.md)'s "host `176`" convention) *before* the guest's own daemon ever calls `chk_host()`. The daemon must already be listening when ITS dials, so the guest boots and starts `smalldaemon` first, and ITS drives second — the opposite of getting this backwards, which was this script's own first bug (an earlier ordering had ITS dial before `smalldaemon` even existed to receive it, which understandably went nowhere).

**It reached the network but didn't help.** ITS's own console shows a real `UT` connection attempt (`CONNECT`, then `NET: RST TIMEOUT` roughly a minute later when nothing answers) and the guest's `IMP PKT: input` trace shows a genuine 11-word inbound message arriving — nothing like the routine 6-word keepalive traffic — confirming ITS's RFC really did transit IMP 6 → IMP 62 → the guest's device. But the guest's own subsequent connection attempt still sent only the RST, meaning `h_up_bm[106]` was not set by that inbound message. Neither `ncpd`'s console output nor any distinctive log line explains why; the most likely reading is that this inbound message from a "new-format"-leader host (ITS; see `imp.369`'s own `IMOLDR: <17_10.>,,0` new-format leader construction) isn't being correctly attributed to host 106 by the guest's receive-side leader handling, landing in the same unexplained `no link`/leader-noise background this project has never fully explained (see the still-open hypothesis in [Wiring into the two-IMP topology](#wiring-into-the-two-imp-topology) above) rather than reaching `hr_rfc()` cleanly. Not chased further — recorded as a real, disproven-for-now idea rather than deleted, since the general approach (make the never-contacted-before host receive something first) remains valid in principle and the script is a reusable, working way to try it again in a future session, including against a different guest fix.

## Patching the daemon (2026-08-30, continued)

**Superseded after the adapter corrections.** This section records why the temporary `rfnm_bm` clear was introduced when the misordered RST could not earn an RFNM. The fresh exact-run evidence in [Control-link RFNM accounting and balanced rerun](#control-link-rfnm-accounting-and-balanced-rerun-2026-08-31) shows that the clear must not remain once output ordering is correct: the real RFNM is now present, and the clear corrupts the daemon's otherwise-balanced protocol-buffer accounting.

With the workaround not panning out, applied the fix the previous section already scoped: clear the just-set `rfnm_bm` bit right after `chk_host()` returns, at its two "about to open a new connection" call sites in `ncpd/kr_dcode.c` (`kr_ouicp()`, the `netopen()`-driven path the guest's `telnet` uses, and `kr_odrct()`, the direct-socket path with the identical structure) — not at its third call site in `rst_all()`, which is startup housekeeping with no immediately-following send to protect.

At that point, an earlier version of [`scripts/research/build-guest-ncpd.py`](../../scripts/research/build-guest-ncpd.py) applied that one-line patch (plus the `#include "probuf.h"` `kr_dcode.c` needed for `rfnm_bm`, which it never required before) to a staged copy of `ncpd`'s 14 `.c` files and rebuilt `Largedaemon` from source with V6's own `cc`, entirely in-guest — the same technique already proven for the guest TELNET client, reused rather than hand-patching the prelinked binary. Three real build issues came up, none of them in the patch itself:

- **A genuine archive gap:** `ncpd/send_pro.c`'s `rst_all()` calls `getl()` (read a line from a `struct io_buf`) to parse `/usr/net/hnames`, and no definition of `getl()` exists anywhere in this preserved tree — it likely lived in a local NOSC utility library (plausibly the `-lj` `ncpd/linkit`'s own link recipe references) that was never captured. Left unresolved, V6's `ld` still produces an `a.out`, but with an undefined symbol this guest's `exec()` then refuses to run at all. Fixed with a minimal, clearly-marked linker-only stub (`GETL_STUB_C` in the build script) — correct here specifically because `/usr/net/hnames` does not exist on this image, so `fopen()` fails first and the code path that would really call `getl()` is never reached at runtime.
- **A self-inflicted format mismatch:** a first attempt linked with `-n -x`, matching `build-guest-telnet.py`'s own single-file build. That produced a "separate I&D" binary with no linker errors, which this guest's `exec()` also silently refused — this project's own deviation, not an archive issue, since `ncpd/linkit`'s real historical recipe never used `-n` at all. Matching a plain link fixed the format but not the `exec()` failure by itself.
- **The real remaining cause:** file ownership. `ncpd/linkit`'s own install step explicitly does `chown daemon; chgrp system; chmod 544` — and that ownership is load-bearing, not cosmetic: `ncpd/smalldaemon.c` calls `setuid(1)` before `execv()`-ing this exact path, so under mode `544` (owner-execute only) the binary must be owned by that same uid or `exec()` fails with a permission error, which is indistinguishable from every other `exec()` failure at the console (`smalldaemon`'s own `"Exec of large daemon failed\n"`). The build script had been `chmod`-ing the freshly-linked binary while it was still owned by `root` (the guest's build session ran as `root`); adding the matching `chown`/`chgrp` fixed it. (`chgrp system` itself still fails with `Who?` — a benign, unexplained gap on this specific `green/unix` image — but `chown daemon` succeeding is what actually mattered, since mode `544` never grants group or other any execute bit.)

**The fix works, confirmed by re-running the exact same connection attempt.** With the patched, correctly-installed `Largedaemon`, `Largedaemon` now actually starts (`smalldaemon`'s exec failure is gone), and the guest's own `IMP PKT: output` trace shows a **second, tenth-word transfer** immediately after the same 5-word RST — `hw_rfc()`'s real RFC, its size (leader plus the 10-byte `hw_buf` `hw_rfc()` always sends) matching exactly. This is the first time in the project's history the guest daemon has been observed actually attempting the real connection request rather than stalling after its own defensive reset. The patch does what it was written to do.

**The connection still doesn't complete, and that turns out to be informative.** Cross-referencing IMP 62's own `hi2`/`MI1` logs shows the RFC arrives at IMP 62's host interface byte-for-byte (`HI2 UDP: ... sequence=518, length=32`, exactly the leader-plus-content size) — but `MI1` traffic in that exact window is, again, unbroken routine routing/keepalive exchange with zero reaction, identical to every earlier RST-only run. The real RFC gets no further than the RST did. That rules out one more hypothesis this session had left open: it is not that the RST specifically confused something and a real RFC would have fared differently — a well-formed, complete, correctly-addressed connection request reaches IMP 62 and still goes nowhere. Whatever stops IMP 62 from relaying this guest's traffic toward IMP 6 is unrelated to daemon-side content or bookkeeping; it is a property of this specific host attachment or its traffic, still not isolated. The original "Isolating the IMP 62 → IMP 6 relay gap" open question above is real and still open — this session's daemon fix closes the bug it targeted but does not, on its own, get a login prompt.

## The actual IMP 62 relay cause: PDP-11 word ordering (2026-08-31)

The apparent relay gap was not a routing-table or firmware dispatch gap. It was a physical interface error in the PDP-11 device model, newly distinguishable only because the rebuilt daemon now emits the full RFC and the exact H316 input trace preserves the received words.

The [January 1976 BBN Report 1822](https://archive.org/stream/bitsavers_bbnimpBBN1_8769843/BBN1822_Jan1976_djvu.txt) states that the high-order bit of each host-interface word is transmitted first. The DEC IMP11-A manual had already established that the hardware is a generic bit-serial interface rather than a source of leader fields; the preserved NOSC driver writes those fields as adjacent PDP-11 bytes. For a regular message to host `106` octal, its first two bytes are therefore `type = 0`, `host = 0106`. In PDP-11 memory that is the little-endian numeric word `043000`; on the IMP wire it must be numeric word `000106`, with `type` in the high byte and `host` in the low byte.

The old `imp_start_output()` did a raw `Map_ReadW()` → UDP-word copy. The exact fixed-daemon run consequently showed IMP 62 receiving `043000` as the first word of both the RST and the RFC. The H316 firmware did not treat that as a regular message addressed to IMP 6, so it produced no corresponding `MI1` message. NOPs had concealed the defect because their zero destination byte makes the two orderings look the same enough to pass the startup exchange.

At this point in the investigation, the then-local `imp11a-device` source swapped the bytes of every output DMA word immediately before handing it to the shared H316 UDP transport (`432080b2`). Input was still unchanged: the NOSC receive buffer deliberately begins with a dummy byte, and the earlier no-conversion run had shown only that input DMA completed without a device fault, not that the daemon decoded the resulting bytes correctly. The later input correction and trace are now published in the pinned `f1ca562e` revision. `scripts/research/two-imp-its-pdp11-telnet.py` and `scripts/research/its-speaks-first-then-pdp11-telnet.py` now also create a run-local IMP 62 configuration with `HI2 noconvert` by default, because the shared configuration's bidirectional conversion is for ITS, not this PDP-11 short-leader attachment.

The controlled rerun `imp11a-telnet-byteorder-20260831T134000Z` used the saved fixed-daemon RL01s and the rebuilt local PDP-11 binary. It confirms the boundary correction end to end: IMP 62 receives the guest RST as `000106 000000 000010 000001 000014` and the full RFC as `000106 000000 000010 000013 000014 000400 000004 000000 000000 013402`; it then emits real `MI1` traffic for each. IMP 6 receives the forwarded RFC and sends it through `HI2` to the KA10/ITS peer. This is direct relay evidence, not an inference from a timeout.

## KA10-side trace: ITS accepts the NOSC header (2026-08-31)

The controlled run `imp11a-telnet-ka10-trace-20260831T131616Z` reused the saved fixed-daemon RL01 images and the local `432080b2` PDP-11 simulator. The TELNET research driver made a run-local copy of the ITS configuration and enabled the KA10 simulator's IMP `CONI`, `CONO`, and `DATAIO` tracing after the existing attachment command; no shared configuration, firmware, media, or protocol conversion changed. The raw logs and generated simulator configurations remain under the external laboratory result directory, not in this repository.

The trace correlates the transaction across every relevant attachment. PDP-11 output sequences 261 and 262 contain the RST and the RFC-bearing message already established in the prior run. IMP 62 forwards both across `MI1`; IMP 6 delivers them through `HI2`; and the KA10 trace shows ITS reading the resulting long-leader messages with `DATI` and then writing replies with `DATO`. On the return path, IMP 6 converts ITS's long leader back to the short form and records `000176 000000 000010 000001 000015 000000 000000`; IMP 62 subsequently delivers the equivalent source-addressed message to the guest as `000106 000000 000010 000001 000015 000000 000000`. Decoded as octal bytes, that is a regular message on link 0 with zero subtype, zero M1, byte size `010`, byte count `1`, zero M2, and opcode `015`: RRP.

The complete outbound NOSC header also matches the historical contract, not merely the first four bytes. The RFC-bearing message begins `000106 000000 000010 000013 000014 ...`, whose first nine octets are type `0`, destination host `106`, link `0`, subtype `0`, M1 `0`, byte size `010`, byte count `000013`, and M2 `0`; its control text follows. The January 1972 Host/Host specification, preserved as [RFC 6529](https://www.rfc-editor.org/rfc/rfc6529.html#section-3), defines exactly that 72-bit header: a 32-bit BBN 1822 leader followed by zero M1, an 8-bit byte size, a 16-bit byte count, and zero M2. It assigns link 0 to control messages, requires byte size 8 there, assigns opcodes 12 and 13 decimal to RST and RRP, and requires an RST recipient to return RRP. [RFC 704](https://www.rfc-editor.org/rfc/rfc704.html) documents the later expansion of the surrounding IMP leader from two to six 16-bit words while preserving the position of host-to-host data. The pinned ITS monitor's own NCP-era [`impold.ncp2`](https://github.com/PDP-10/its/blob/0f7d67997f9f5d30208e117e73272031e74f16b9/src/system/impold.ncp2#L246-L276) independently locates M1, byte size, byte count, and M2 in that same NCP leader word. ITS's observed RRP is direct executable confirmation that the header passed those checks, so there is no firmware or ITS header-rejection condition to explain and no type-1 error emitter in this exchange.

The two IMP-generated messages immediately following the guest sends are also normal acknowledgements, not errors: IMP 62 records `002506 000000`, whose old-leader message-type field is 5, RFNM. The preserved daemon's `impi.h` agrees that type 5 is `iri_rfnm`; type 1 would have been `iri_erldr`, but no such network message appears in the correlated window.

The misleading console text has a different source. The preserved `kr_dcode.c` contains the literal `kr_rcv: Data from host zero`, and `kread.h` shows that the bytes printed after it begin with `kr_op`, then `krr_type`, `krr_host`, `krr_link`, and `krr_sbty`. The visible `ze` is a truncated rendering of `zero`, and the first printed `1` is `kri_rcv`, not an IMP message type. For the returned regular message, the network's first word is `000106`, meaning the two bytes `0, 106`; the current input path copies that numeric word unchanged into PDP-11 memory with `Map_WriteW`, which stores its low byte first. The guest consequently reads leader type `106` and host `0`, producing exactly the logged `1 106 0 0 0` and discarding the valid RRP/control traffic before the NCP can use it.

This is new receive-side evidence, not a reopening of the settled output fix: `432080b2` remains the demonstrated correction for guest-to-IMP serialization, and the IMP 62 relay remains proven. No compatibility conversion was added in this investigation. The next bounded action was to align the IMP11-A input DMA presentation with the preserved driver's byte-structured leader contract, then rerun this same correlated transaction and require the guest to decode the RRP and subsequent ITS control messages before treating a TELNET timeout as an application-layer failure.

## Corrected input DMA and correlated rerun (2026-08-31)

The published simulator correction is deliberately at the adapter boundary only. `4509a22` byte-swaps each received network-order 16-bit word before `Map_WriteW`; it shares the same small conversion helper as output, whose established `432080b2` behavior is unchanged. The real driver reads the initial eight leader bytes word-aligned, then begins a separate buffer with the ninth (discardable) leader byte, so every DMA transfer has the same byte-presentation requirement. `f1ca562` adds a packet-debug record after the store, making the physical evidence visible without changing device behavior.

A scheduled poll then consumes a no-data, non-READY probe while leaving that DMA pending and its interrupt count unchanged; only the later empty final preserves the residual, sets `ENDMSG`, and raises exactly the second interrupt. ## Control-link RFNM accounting and balanced rerun (2026-08-31)

At this stage, [`scripts/research/build-guest-ncpd.py`](../../scripts/research/build-guest-ncpd.py) staged narrowly-scoped `PBTRACE` records in `send_pro.c` and `ir_proc.c` for host `106`. The first correlated result, `imp11a-telnet-pbtrace-20260831T160605Z`, used the instrumented version of the then-current staged daemon and proves the contradiction exactly:

## Receive continuation root cause and usable TELNET proof (2026-08-31)

The complete returned control stream in `imp11a-telnet-rfnm-balanced-20260831T161143Z` already contained everything the outgoing ICP required. After the RRP, PDP-11 input sequence `10` carries three NOPs and ITS's STR for the contact connection, mapping foreign socket `027` to local socket `02000` with byte size `040`; sequence `12` carries RTS from foreign socket `01000` to local socket `02003` on data link `3`; sequence `14` carries STR from foreign socket `01001` to local socket `02002` with byte size `010`; and sequence `16` later carries the contact CLS. The preserved daemon's socket conventions and the network's fields agree.

Trace-only build `imp11a-ncpd-sktrace-build-20260831T173146Z` added bounded host-106 `SKTRACE` records for host-host decoding, outgoing ICP construction, socket requests and candidates, match decisions, transitions, and kernel setup/modify/ready writes. Control run `imp11a-telnet-sktrace-control-20260831T173527Z`, still using the old pinned simulator behavior, proves the outgoing half was correct: it created the host-106 contact request with local socket `02000`, foreign socket `027`, and the expected kernel setup. It then recorded no inbound `hr_dcode()` trace at all even though the device log recorded the returned multi-word transport frames. The failure was therefore before daemon decoding, not within its socket-state matrix.

The old adapter clipped each UDP frame to the guest's current four-word DMA request, discarded the surplus, replaced `IWC` with the negative delivered count, asserted `ENDMSG`, and completed the read. Flag-only final frames were ignored. The preserved guest contract is the opposite: the driver exposes the hardware's residual `IWC`, and its receive interrupt handler rearms for a continuation only when `ENDMSG` is clear and `IWC` reached zero. The old completion consequently delivered only the first eight bytes (64 bits) of the 72-bit leader and told the kernel it was a complete message, making every returned STR/RTS/CLS body disappear before `hr_dcode()`.

Published simulator commit [`2722eef44f68642eaab9f5d4e989ccd26e55e7de`](https://github.com/brfid/imp11a-simh/commit/2722eef44f68642eaab9f5d4e989ccd26e55e7de) corrects that boundary. It keeps a dedicated retained input frame and cursor, separate from the output scratch buffer; advances an internal 18-bit DMA address; increments `IWC` toward zero; interrupts without `ENDMSG` when a guest buffer fills; continues receiving when a non-final frame ends with buffer space left; and completes with `ENDMSG` only when final data is exhausted or an empty final closes an active message. Reset, input-half reset, attach, and detach clear retained state, the poller, and the receive interrupt. Fixed DIB interrupt-ack callbacks return input vector `0274` and output vector `0124`, so later generic Unibus-table rebuilds cannot erase them.

The corrected adapter passes Open SIMH's `-Werror` PDP-11 build and internal `RegisterSanityCheck`, plus the focused real-CPU regression described above. First application rerun `imp11a-telnet-input-continuation-20260831T174934Z` reached `Connection open`, assigned an ITS TTY, and displayed the ITS banner; its then-hard-coded `time` line was not a valid ITS colon command. Run `imp11a-telnet-usable-20260831T180633Z`, from the same successful trace build and with the driver sending `:time`, first closed the application-level criterion. Clean build `imp11a-ncpd-sktrace-verified-build-20260831T190000Z` and run `imp11a-telnet-usable-verified-20260831T191000Z` reproduced that success after the first builder and driver hardening pass. Independent fail-closed review then caught one remaining future-run risk: an install-copy failure could leave the old daemon at its destination. The current builder removes that destination, proves it absent, copies the new artifact, and compares the installed size with the linked `a.out`. Fresh build `imp11a-ncpd-sktrace-final-build-20260831T192000Z` exercised those checks, and exact final run `imp11a-telnet-usable-final-20260831T193000Z` reproduced the usable session from that image and published simulator commit:

1. The returned contact STR reaches `hr_dcode()`, matches the outgoing RFC-wait socket, and records `SKTRACE transition ... rfcw->open`.
2. The returned RTS and data STR create and match the two data sockets; kernel setup/modify calls culminate in `SKTRACE kw-ready id=121132 code=0`.
3. The guest prints `Connection open`, then receives `MIT Dynamic Modelling PDP-10`, `KA ITS.1652. DDT.1549.`, `TTY 53`, `Welcome to ITS!`, and `Happy hacking!` from host 106.
4. The remote `:TIME` command returns `(Please Log In)`, `The time is 16:03:35 EDT.`, `Today is Sunday, the 31st of August, 2025.`, and `KA ITS 1652 has run for 51 seconds.` on the PDP-11 console. The hardened driver requires the open transition and remote time text before returning success; it exited zero and cleaned up the topology. Correlated IMP and KA10 logs remain in that exact result directory.

The legacy client prints `Possible protocol error! command = 376, option = 3.` during TELNET option negotiation, interleaved with the greeting. It does not close or corrupt the proven session: the ITS banner completes and the subsequent remote command receives a structured response. This is a narrow interoperability diagnostic worth preserving for follow-up, not a failure of the application proof.

Evidence hygiene matters for this sequence. `imp11a-ncpd-sktrace-build-20260831T173057Z` was an exact-anchor preflight failure and produced no guest artifact; `imp11a-telnet-sktrace-control-20260831T173222Z` was run inside a sandbox that denied loopback binds and is invalid.
