# DEC IMP11-A device model

**Status:** Device model implemented and verified in isolation; the real NOSC `green/unix` kernel boots to a login shell against it, with the NCP daemon binary and `/dev/ncpkernel` in place. The daemon (`smalldaemon` execing `Largedaemon`) has now been started against the live device: doing so surfaced and led to fixing a real device bug (see [Starting the NCP daemon](#starting-the-ncp-daemon) below). The device has since been wired into the same two-IMP fabric proven for the two-ITS smoke, alongside a real ITS host 106, with no PDP-11-specific topology change needed (see [Wiring into the two-IMP topology](#wiring-into-the-two-imp-topology) below): the guest has received real, substantive, multi-word network traffic for the first time, correctly exercising the previously-untested short-completion input path. A genuine application-level NCP exchange (guest TELNET) has not been proven — the archive has no prelinked TELNET client, and building one from source is a separate, unstarted task.

This continues the plan in [PDP-11 Network UNIX as the first heterogeneous host](pdp11-network-unix.md). It records the register-level design and the verification performed so far for the new IMP11-A device.

## Register map

Reconstructed from the DEC IMP11-A technical manual and from the register-level behavior of the SRI/NOSC "imp11a" kernel driver in the preserved Network UNIX V6 source (register addresses, bit positions, and hardware behavior are historical facts about the physical device, not the driver's expression; no driver source is reproduced here).

Fixed base `0172410`, 12 words (`030` octal / 24 bytes), non-autoconfigured:

| Offset | Register | Notes |
|---|---|---|
| 0 | OWC | output word count, two's-complement |
| 2 | SPO | output start address (low 16 bits) |
| 4 | OSTAT | output status |
| 6 | OMAINT | output maintenance |
| 10-16 | (unused) | real hardware does not decode this range |
| 20 | IWC | input word count, two's-complement |
| 22 | SPI | input start address (low 16 bits) |
| 24 | ISTAT | input status |
| 26 | IMAINT | input maintenance |

Two fixed interrupt vectors, `0124` (output) and `0274` (input). These are not the standard DEC `vec, vec+4` pair that Open SIMH's generic multi-vector DIB assignment loop assumes for a device with `vnum > 1`, so the DIB's `vec` field is left `0` (suppressing that loop) and `imp_reset()` writes `int_vec[IPL_IMPRX][INT_V_IMPRX]` and `int_vec[IPL_IMPTX][INT_V_IMPTX]` directly.

Status-register bits (shared layout, some read-only in one half): `GO` (start), `RST` (self-clearing reset), `IENAB` (interrupt enable), `XMEM` (2-bit extended address, giving 18-bit Unibus DMA addressing from the 16-bit SPO/SPI plus these bits), `OENDMSG` (output: this buffer ends the message), `WRTENBL` (input: enable receive), `HMASRDY` (input: pulse to tell the peer this host is up), `MASRDY` (input, read-only: peer/IMP reports ready), `ENDMSG` (input, read-only: a full message was received), `DONE` (output, read-only: transfer complete), `TIMOUT` (read-only: transfer timeout, not yet driven by any real fault condition).

## Wire protocol

The device reuses the H316 device family's existing UDP transport (`H316/h316_udp.c`: `udp_create`/`udp_send`/`udp_receive`), unchanged, exactly as the KA10 NCP-mode IMP device (`PDP10/kx10_imp.c`) already does to reach an H316 IMP's host port. This is the same shared component the two-ITS gate depends on, MIT-style licensed with a no-name-in-advertising clause, already vendored into both `ka10-simh` and `open-simh`.

The actual UDP payload is a `UDP_PACKET` struct: `magic` (`"H316"`, `htonl`), `sequence` (`htonl`, per-link monotonic), `count` (`htons`, word count of the data that follows), then `count` data words (`htons` each). The device-level convention layered on top, shared with `h316_hi.c` and `kx10_imp.c`, is that the first data word is a flags word (`PFLG_FINAL` = 1, `PFLG_READY` = 2) and the rest is the actual message content. None of this needed to be invented; it was fully determined by reading the existing shared code before writing anything new.

`h316_udp.c`'s "Connect=" UDP mode means each link behaves like a connected socket: it only accepts datagrams from the exact configured remote host and port. This tripped up the first verification attempt (see below) and is worth remembering for any future test harness against this device.

## Verification performed

Before any guest driver ran against it, the device was verified in isolation: a real CPU-executed bus write (not a debugger register poke, which bypasses the write handler entirely) drives the device correctly, in both directions, using hand-assembled PDP-11 machine code deposited into memory and executed with `step`. (The real `green/unix` guest driver has since run against it too; see [Booting green/unix under this device](#booting-greenunix-under-this-device) below.)

- **Output:** `MOV #imm,@#addr` instructions set SPO/OWC then wrote OSTAT with `GO|OENDMSG|IENAB`. The device read the guest memory word via `Map_ReadW` and transmitted it. The resulting UDP datagram was captured and decoded by hand: magic, sequence (0, first packet on the link), count (2), and both data words (flags `3`, and the exact guest memory content) all matched exactly.
- **Input:** a hand-built `UDP_PACKET` (flags `PFLG_FINAL`, two data words) was sent to the device's attached port from a source bound to the exact configured remote port (required by the "Connect=" filtering above). Guest instructions then wrote SPI/IWC/ISTAT with `GO|WRTENBL|IENAB`. The device's synchronous re-check on that write (not a scheduled poll) picked up the already-queued datagram immediately, `Map_WriteW`'d both data words into the exact requested guest memory addresses, and set ISTAT to `IENAB|ENDMSG`.

The build also passes Open SIMH's own `RegisterSanityCheck` self-test.

## Open questions for guest testing

Updated after starting the real daemon against the live device; see [Starting the NCP daemon](#starting-the-ncp-daemon) below for how each of these was actually resolved or narrowed.

- Whether the guest ever chains multiple output buffers into one message: not observed in any live run so far. Every guest-originated send seen so far — the three startup NOPs and the daemon's ongoing background keepalive traffic — is a single `OENDMSG`-terminated buffer, matching the current device's one-buffer-per-message model. Only small (2-word) messages have been exercised; a TELNET/FTP-sized transfer may still chain and remains untested.
- The exact contract for a short or partial input completion (how much of IWC the guest expects back when fewer bytes arrive than requested): still untested. No live run has yet delivered a real multi-word message to the input side; the external test peer used so far only sends flag-only (zero-data) keepalives.
- `TIMOUT` and the general error-summary bit are defined but nothing yet drives them; still untested.
- `DEBTAB` (`SET IMP DEBUG=REG;INT;PKT`) is now implemented, and is what made the findings below observable.

## V6 base: reproducing the pristine root filesystem

The official [SIMH UNIX V6 software kit](https://sourceforge.net/projects/simh/files/Software%20Kits/UNIX%20v6%20for%20the%20PDP-11./) (Caldera/Ancient-UNIX licensed) boots to a login prompt on this same Open SIMH build unmodified: `SET CPU 11/34`, `SET CPU 128K`, `SET CPU NOAUTOCONFIG`, attach its four RK05 images, `BOOT RK0`, then `unix` at the `@` prompt. This confirms the IMP11-A changes above do not disturb the baseline PDP-11 simulator.

Reproducing that same root/source/doc filesystem set from the raw historical distribution tape (rather than the prebuilt kit) turned out to need a different method than the one documented method assumes. The [`eblanton/unix-v6-install`](https://github.com/eblanton/unix-v6-install) reference (`94df669009311ce0e693aa326142732f77796813`, no declared license, used here only as a methodology reference, not copied into any repository) drives this via an in-simulator `tmrk` meta-command that does not exist in Open SIMH; every attempt using it hangs indefinitely on an unmatched `expect "="`.

Its own tape-processing tool (`v6enb`'s `enblock`, converting a raw historical tape image into SIMH's `.tap` container format) still works once its 2001-era C is coaxed past current clang's default-error implicit-function-declaration checks (`-Wno-error=implicit-function-declaration -Wno-error=implicit-int`). The resulting `.tap` file is exactly 12,100 fixed 512-byte tape records plus a tape mark: the first 100 are a raw bootstrap area, then three 4,000-record filesystems back to back (root at tape offset 100, `/usr/source` at 4,100, `/usr/doc` at 8,100). Because a SIMH `.tap` record is just a length-prefixed byte range, those three filesystems can be extracted directly, at the host level, straight into zeroed RK05-sized target files, with no PDP-11 execution involved at all: [`scripts/research/extract-v6-tape.py`](../../scripts/research/extract-v6-tape.py). That reproduced root filesystem boots and logs in identically to the official kit (`rkunix`, root, no password) with the historically correct embedded clock (`Fri Oct 10 12:29:44 EDT 1975`).

This matters here because it is the same technique the remaining work depends on: getting the prelinked `green`/`green47` kernels and the NOSC NCP daemon and applications onto a filesystem this simulator can boot does not require rebuilding anything from source (they are already built), only correctly placing existing bytes.

## Injecting files directly into a V6 filesystem image

Getting the prelinked `green/unix` kernel and the NCP daemon onto a filesystem needed a way to place already-built binaries directly, since there is no source to compile in place and no working in-simulator tape-write path. [`scripts/research/v6fs.py`](../../scripts/research/v6fs.py) implements exactly the on-disk structures in `ino.h`/`filsys.h`: superblock free-list allocation (including the classic V6 trick where the block about to be handed out is first read as the next free-list chunk), inode allocation by linear scan for `i_mode == 0`, small (direct-block) and large (single-indirect) file writes, and directory-entry insertion. It has a small CLI (`mkdir`, `put-file`, `mknod`, `lookup`) as well as being importable.

The first version had a real bug, caught by testing against a live boot rather than only re-reading the bytes with the same tool that wrote them: reusing a deleted (`ino == 0`) directory slot beyond the directory's current logical size wrote valid bytes that the kernel's own directory scan, bounded by the inode's `size` field, never reached. A file placed this way was invisible to `ls`/`open` even though it was genuinely on disk. Fixed by tracking size explicitly and only ever treating a slot as reusable when it falls within `[0, size)`; anything past that must grow `size` by exactly one 16-byte entry, whether or not it also requires a new block.

## Booting `green/unix` under this device

Two more facts had to be pinned down before a boot attempt meant anything, both by disassembling the actual `green/unix` a.out binary rather than guessing, since NOSC's own kernel-config table was not preserved in the archive:

- **`/dev/ncpkernel`'s major number.** `cdevsw` (found in the binary's data segment via its own symbol table entry) is an array of `{open, close, read, write, sgtty}` function-pointer quintuples. Scanning it for the address of `_ncpopen` (the daemon-facing entry point in `ncpio.c`, not the lower-level `_impopen`/`_impread` internal to the driver) lands at index 25, i.e. major **5** — confirming the number already recorded in [pdp11-network-unix.md](pdp11-network-unix.md) independently.
- **Root and swap devices.** The `_rootdev`/`_swapdev` data symbols decode directly to `(1,0)` and `(1,1)`: `bdevsw` entry 1 is the RL driver (`_rlopen` at that slot), so root and swap are both on RL, unit 0 and unit 1 respectively.

Booting the resulting image over Open SIMH's `RK0` failed immediately (`panic: iinit`, `err on dev 1/0`) because attaching the very same bytes as `RK0` presents major 0, not the major-1 RL device the kernel expects — a software-level dispatch mismatch, not a data problem. Attaching as `RL0` instead got further but failed silently at the boot-ROM prompt (`@`) for every filename, including the already-known-good `rkunix`: the disk content's boot block (byte-identical to the RK-formatted image) contains RK-specific low-level disk I/O, which does not work when the CPU is executing it against an RL-attached device. The fix, taken directly from the `eblanton/unix-v6-install` `pristine-rl` script's own logic (copying an RL-native boot block over before use), was to overwrite block 0 with the boot block from the real RL02 reference image (Tim Shoppa's `unix_v6.rl02`, TUHS-hosted, methodology reference only). That RL bootstrap prompts with `!`, not `@`. With that block 0 and a second RL01 unit attached for swap (`err on dev 1/1` without one — `swapdev`, not root, once root itself was reachable), `green` boots cleanly to `login:` and root logs in.

The confirmed-present, confirmed-correct result on a live boot: `/dev/ncpkernel` (`crw-rw-rw- root 5, 0`), `/green` (42,988 bytes, matching the source file exactly), and `/usr/net/etc/Largedaemon` (17,648 bytes, matching exactly). This is the actual NOSC-built kernel — not a synthetic test program — reaching a shell with the new IMP11-A device attached, root and swap on RL, and the NCP daemon binary in place at the path its own `smalldaemon` launcher (recovered by reading its embedded strings) expects. [`scripts/research/boot-green-with-imp.py`](../../scripts/research/boot-green-with-imp.py) reproduces this boot and check.

## Starting the NCP daemon

`/usr/net/etc/smalldaemon` (954 bytes, matching the archive's copy exactly) was already present on the working root image alongside `Largedaemon`, though not yet run. Starting it — `open("/dev/ncpkernel", 2)` then `execv` into `Largedaemon` on that same file descriptor, per its own source — drives `ncpopen()` → `impopen()` → `imp_init()` in the real preserved driver (`ncpk/drivers/imp11a.c`, `ncpk/drivers/impio.c` in the pdp11/network-unix-v6 tree), the exact register sequence this device model exists to answer. Reaching that required adding the `DEBTAB` support flagged as missing above (`SET IMP DEBUG=REG;INT;PKT`, plus `SET DEBUG -n <file>` for the destination), reusing the same `DBG_REG`/`DBG_INT` idiom as the sibling `pdp11_dup.c`. [`scripts/research/start-daemon-with-imp.py`](../../scripts/research/start-daemon-with-imp.py) reproduces the boot-and-start; [`scripts/research/udp-test-peer.py`](../../scripts/research/udp-test-peer.py) is the minimal external peer used below.

**A real device bug, found only by running the real driver.** The first attempt hung: `smalldaemon` opened cleanly and the console printed `IMP:Reset`, but the daemon never progressed past it, and `IMP:Init` never printed. The debug trace showed why: `imp_rd`'s `ISTAT` case OR'd `IMP_MASRDY` into every read whenever the device was attached (`imp_link >= 0`), regardless of whether any peer had ever actually signaled ready. The real driver's `imp_init()` does exactly `while (IMPADDR->istat & imasrdy) sleep(&lbolt, 0);`, intending to wait until a peer's READY is seen — with the bug, that condition was permanently true from the moment of attachment, so the real driver spun forever, before ever enabling interrupts or sending anything, with or without a peer on the other end. This is why the isolated bus-write verification recorded above never caught it: that test hand-poked `GO|WRTENBL` directly and never ran the driver's own `imp_init()`, so it never read `ISTAT` in a state where MASRDY needed to still be zero. Fixed by dropping the on-attach synthesis; `ISTAT` now reports exactly `imp_istat`, and MASRDY is set or cleared only by `imp_check_input()` from a real received `PFLG_READY`, matching the register map's own "peer/IMP reports ready" description.

**With the fix, the real driver's startup sequence matches the reconstructed source register-for-register**, observed over `SET IMP DEBUG`: `imp_reset()`'s explicit software `RST`-set-then-clear on both halves (the driver does not rely on hardware self-clear, even though the real vector/CSR behavior is self-clearing); one `HMASRDY` pulse from `set_HMR()`, correctly producing one outbound READY-flagged keepalive datagram; `IENAB` enabled on both halves; exactly three startup NOPs sent from `impopen()`'s init loop, each a single 2-word `OENDMSG`-terminated buffer (`OWC`/`SPO`/`GO` written once per NOP, no buffer chaining for a message this size); `IMP:Init` printed; and the first input leader read armed (`SPI`/`IWC`/`ISTAT` with `GO|WRTENBL`). All of this had never been exercised by real guest code before this session.

**The daemon keeps talking after startup.** Once running, `Largedaemon` continues sending identically-shaped 2-word NOP/keepalive probes on its own periodic timer, independent of whether anything ever answers — a real, previously undocumented steady-state behavior worth expecting once the two-IMP topology is wired up, not just the three one-time startup NOPs.

**Proving delivery needed a genuine external peer, and two test-setup mistakes had to be found and corrected first**, both worth recording for whoever runs this next:

- Attaching with equal local and remote ports (e.g. `9000::9000`) makes the device receive its own transmissions back as if a perfectly-echoing peer were attached — every self-sent packet loops straight back in. This produced a long, misleading run of what looked like protocol activity before the mechanism was understood.
- `ATTACH IMP <port>:localhost:<port>` resolves `localhost` to IPv6 `::1` on the tested machine, `lsof` confirmed. An external test peer bound to IPv4 `127.0.0.1` on the matching port never sees any of it, and outbound sends toward that unreachable IPv6 endpoint get OS-level connection-refused errors that Open SIMH's TMXR layer reports, confusingly, as `tmxr_put_packet_ln() failed with error Console Telnet connection lost`, once per further send attempt. Using an explicit `127.0.0.1` in the attach string forces IPv4 and fixes this. [`docs/runbook.md`](../../docs/runbook.md) already pins every configured peer in this project to IPv4 loopback for exactly this class of mismatch; this is the same gotcha, independently rediscovered against this device.

With both corrected, a minimal external Python process (not a peer NCP/IMP implementation — just enough of the `h316_udp.c` wire format to send a periodic READY-flagged keepalive and log what it receives) exchanged real, independently observed traffic with the guest: 30 datagrams delivered guest-to-peer over the run, decoded outside the simulator entirely and matching the debug trace's own `OWC`/flags exactly, and the guest's `MASRDY` bit now correctly tracked the peer's real `PFLG_READY` signal through `imp_check_input()` rather than the removed synthesis. The peer in this run only ever sent flag-only (zero-data) keepalives, so the input side never received a real multi-word message and never fired an input interrupt; the short/partial-input-completion contract and `TIMOUT`/error-summary handling are consequently still untested; a real peer that answers with actual message content is needed for that, which the two-IMP topology step will naturally provide.

**One anomaly remains unexplained.** The guest console prints `IMP: Phantom Out Int` — the driver's own message for an output interrupt arriving while its software bookkeeping (`impotab.d_active`) already reads zero — exactly once per run, immediately after the three startup NOPs complete. It reproduced identically in the self-loopback run and in the corrected external-peer run, so it is not an artifact of either test-setup mistake above, but its root cause has not been isolated (a candidate: something about how the three back-to-back `impstrat`/`iowait` completions interact with this device's fixed 100-tick output-completion scheduling). It has had no observed adverse effect — boot and the daemon both continue normally — so it is recorded here rather than chased further this session.

The debug-tracing and `ISTAT` fix described above are committed locally in the lab's `open-simh` checkout (`a56c68ed`), on top of the branch's existing device commit. The run logs (console transcript, register/interrupt/packet debug trace, and the external peer's independent capture) are immutable per-run evidence directories under the lab's `results/`, per [`docs/runbook.md`](../../docs/runbook.md); they are not committed to this repository, consistent with [`NOTICE.md`](../../NOTICE.md).

## Wiring into the two-IMP topology

The two-IMP fabric already proven for the two-ITS smoke — IMP 6 and IMP 62 joined by `mi1`, each with a host on `hi2` — needed no PDP-11-specific change at all. [`config/imp/its-pair/imp6.simh`](../../config/imp/its-pair/imp6.simh), [`config/imp/its-pair/imp62.simh`](../../config/imp/its-pair/imp62.simh), and [`config/hosts/its106-pair.simh`](../../config/hosts/its106-pair.simh) were reused byte-for-byte: ITS host 106 stayed on IMP 6's `hi2` exactly as in the existing pair, and the `green/unix` guest took IMP 62's `hi2` in place of the second ITS host, attaching over the identical H316 UDP transport and flag-word convention any host uses there. [`scripts/research/two-imp-its-with-pdp11.py`](../../scripts/research/two-imp-its-with-pdp11.py) drives all four processes (IMP 6, IMP 62, ITS host 106, and the PDP-11 guest) and reproduces the run below; it is a manual smoke check, not the formal `two-its-controller.py` — no port lease, no run manifest, informal readiness checks against the same watchdog-light and console-banner text [Gate 4](../test-plan.md) uses formally.

Both H316s reached modem-up (`077400`) and host-link-up (`075400`) watchdog lights, ITS host 106 booted cleanly to its system-console banner and a login prompt exactly as it does in the existing two-ITS smoke, and the PDP-11 guest attached to IMP 62's `hi2` and started `smalldaemon` without incident. ITS logged one benign `IMP: Interface-reset msg` (the same telemetry line [the test plan](../test-plan.md) already documents as expected, not an error) and was otherwise undisturbed for the full run; its media was booted from a fresh per-run copy, and the shared prepared source was confirmed unmodified afterward.

**This is the first time the device has received real, substantive, multi-word traffic from a genuine external network, and it did so correctly.** Where every prior test peer (self-loopback, or the minimal external Python one) only ever produced flag-only keepalives, real traffic now arrives through the live two-IMP path: 149–256 real input interrupts across two runs (25s and 60s settle windows), every one of them a genuine `short completion` — the guest's 4-word (8-byte) leader-read buffer against a 6-word arriving message — exercising the previously-untested short/partial-input-completion contract for the first time, and getting the intuitively correct answer with no guest-visible fault: the device delivers as many words as the requested buffer holds and reports that count back through `IWC`, and the guest driver's leader-read/re-arm loop keeps running cleanly across all of them. `TIMOUT` and the error-summary bit still saw no activity; buffer chaining is still only evidenced in the negative, for small messages, same as before.

**A new, real, only-partially-explained observation:** `Largedaemon` logs `no link:  1   0  17   7   0` once per received message (`ncpd/hr_proc.c`'s `hr_data()`, printed when a regular host-to-host message arrives for a host+link with no matching open connection). Cross-referencing IMP 62's own `hi2`-debug log (already enabled in the reused config) for the same window shows the likely source: `HnFOUT` (host output) events emitting a real 2-word message (`002000 000000`, octal, actual content words rather than a bare flags-word keepalive) toward the PDP-11's port on its own initiative, distinct from and in addition to the ordinary 1-word `PFLG_READY`/`PFLG_FINAL` ready-bit pulses (`HnUNXP`/`HnRDY`, already correctly handled by this device's existing `count == 1` keepalive short-circuit). The most likely explanation is that this is standard 1822 host-interface traffic — plausibly routing or interface-status information the IMP subnet delivers to any attached host — that a real IMP11-A's own hardware would most likely classify and absorb rather than hand to the host as ordinary message content the way this device's current, deliberately minimal wire model does; this device has no concept yet of separating 1822 leader/control content from host-addressed application data, only the `PFLG_READY`/`PFLG_FINAL` flag word already borrowed from the shared transport. This is recorded as a well-reasoned hypothesis, not a confirmed root cause — nailing it down further would mean reading the BBN 1822 specification and the DEC IMP11-A manual's leader-format sections directly, which has not been done yet this session, per the project's own standing guidance to consult primary historical documentation before treating an investigation as stalled rather than guess further.

An application-level proof (guest TELNET to ITS host 106, per the original plan) remains out of reach for a different reason than the network layer: the preserved archive has no prelinked, ready-to-run TELNET client. `Largedaemon` and `smalldaemon` were prelinked and needed no build step; `ncpp/tel-u/telnet.c` and its companions are source only, and `ncpp/tel-s/svrtel.o` is an unlinked relocatable object, not an executable — a scan of every file in the preserved tree found exactly two ready-to-run, application-facing network binaries, both already in use. Building a working TELNET client from that source — in-guest with V6's own `cc`, or via a modern cross-toolchain — is a real, separate undertaking, not attempted this session.
